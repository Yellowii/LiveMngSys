GameQueue 后端规则（贡献值简化版）

本文只定义本场直播的后端额度、权限、队列生命周期和日志规则。用户弹幕的先后排序及车位处理，以 GameQueueRules.txt 为准。

一、核心简化原则

1. 不再把钻石贡献预先拆成“99贡献”和“299贡献”两种权限。
2. 后端只维护一个本场可用贡献值余额，用户通过弹幕决定将余额用于上车、超车或加班。
3. 会员身份和星守护身份只影响贡献值换算及对应费用，不自动创建车位。
4. 所有成功操作都立即扣除对应贡献值；贡献值不足时整条指令拒绝，不部分执行。
5. 基础、置顶和加班仍是三个独立的队列状态；贡献值余额是唯一的消费依据。
6. 上车功能开关只控制普通“上车”指令；当前场次为OPEN时，超车不受该开关影响。

二、本场贡献值计算

1. 普通钻石贡献

普通钻石贡献值 = 本场有效礼物总值 - 会员身份相关数值 - 星守护相关数值。

以下礼物可以计入普通钻石贡献：不属于会员和星守护的其他礼物。贡献值按本场累计，进入用户的 contributionBalance。

2. 星守护换算

- 每开通1个星守护，自动增加398贡献值。
- 年费星守护按398 × 12增加贡献值，即每个年费星守护增加4776贡献值。
- 星守护换算只在当前直播场次有效，关播后不能带入下一场。
- 星守护不再单独发放“上车权限”或“超车权限”，只增加贡献值余额。
- 用户是否上车、超车或加班，完全由对应弹幕指令决定。
- 一个星守护对应的398贡献，可以消费为1次上车（99）+1次超车2局（299），也可以消费为1次加班2局（398），不能重复计算。
- 年费星守护的4776贡献在本场可用于主队列上车和超车，主队列仍受最多6局的现行规则约束；同时加班最多可使用6局，均不会自动创建车位。

3. 会员身份

- 会员拥有无限基础上车资格，不需要为“上车”扣除99贡献。
- 会员不自动拥有超车权限，超车仍按超车贡献值扣除。
- 会员不自动拥有加班局数；会员加班仍需要普通贡献值余额。
- 会员的基础车位数量限制仍按 GameQueueRules.txt 执行：同一场同时只能存在1个未完成基础车位，完成后且功能开启时可以再次发送“上车”。

4. 贡献值账本

每个用户每个 sessionId 维护：

```text
ordinaryContribution
starContribution
totalContribution
consumedContribution
contributionBalance
```

计算方式：

```text
totalContribution = ordinaryContribution + starContribution
contributionBalance = totalContribution - consumedContribution
```

同一份礼物、星守护或订单只能入账一次，必须使用 giftEventId 或 orderId 做幂等校验。

三、弹幕消费规则

1. 上车

弹幕：`上车`

| 用户类型 | 消费 | 结果 |
| --- | ---: | --- |
| 会员 | 0贡献 | 增加1个基础车位，默认2局 |
| 非会员 | 99贡献 | 增加1个基础车位，默认2局 |

处理条件：当前场次为OPEN，且上车功能已开启。非会员贡献值余额不足99时，拒绝本次上车，不扣除贡献值。

2. 超车

超车以2局为一个消费单位，并根据用户是否具有当前基础支持计算费用：

| 用户状态 | `超车2局` | `超车4局` | `超车6局` |
| --- | ---: | ---: | ---: |
| 会员 | 299贡献 | 598贡献 | 897贡献 |
| 非会员当前已有基础车位，余额>=398 | 398贡献 | 796贡献 | 1194贡献 |
| 非会员当前已有基础车位，余额为299~397 | 扣299并转移基础车位 | 不适用 | 不适用 |
| 非会员且当前没有基础车位 | 398贡献 | 796贡献 | 按4局处理，最高796贡献 |

说明：

- 上表表示请求局数全部生效时的费用。实际处理必须先按 GameQueue 规则计算本次实际进入超车队列的局数 `effectivePriorityGames`，再计算费用；该数包含新增局数和从基础车位转入的局数。
- `超车费用 = effectivePriorityGames ÷ 2 × 每2局单价`。没有进入超车队列的局数时拒绝指令且不扣贡献。
- 无基础车位时，置顶区总局数硬上限为4局，不能通过任何超车指令达到6局。
- 无基础车位发送`超车6局`时，按`超车4局`处理；首次从0局增加到4局时扣796贡献，已有2局时只增加2局并扣398贡献，已有4局时拒绝且不扣贡献。
- 例如：有基础车位的2局车位被`超车2局`转入置顶区时，按进入超车队列的2局扣299贡献；有基础车位发送`超车6局`并按主队列规则实际进入置顶4局时，扣598贡献。
- 每2局单价根据接受指令前的状态确定；指令执行中即使基础车位被转移或移除，本次单价也不改变。
- 当前场次必须为OPEN；超车不检查上车功能开关，即使普通上车功能关闭，只要贡献值和队列上限满足，仍可超车。
- “当前基础支持”指会员身份或当前仍存在的基础上车车位。
- 非会员已经通过扣除99贡献进入基础队列时：余额>=398，扣398并新增超车批次，基础车位保留。
- 非会员已有基础车位但余额为299~397时，`超车2局`走降级路径：扣299，将当前最前基础车位转入超车队列并移除原基础位置；`超车4局`和`超车6局`不适用该降级路径。
- 非会员没有基础车位时，发送`超车2局`必须余额至少398；扣398后直接加入超车队列，但不创建基础车位。
- 非会员已有基础车位时，余额500发送`超车2局`属于第一条路径：扣398、新增2局超车批次、基础车位保留，余额剩102。
- 非会员基础车位转入超车队列时，转移的是当前最前的基础车位；转入批次按超车指令接受时间进入置顶区。
- 超车不再预先发放“99基础权限”和“299超车权限”，只按指令发生时的用户状态、贡献余额和局数计算。
- 用户不在基础队列时，仍受主队列规则限制，不能因为贡献值充足而绕过置顶局数上限。
- 指令成功后，生成对应的超车批次；后续超车不能回到用户原来的批次位置。
- 贡献值不足时整条指令拒绝，不扣除部分贡献值。

3. 加班

加班队列独立于基础区和置顶区，用户不需要先进入基础队列即可发送加班弹幕，但必须有足够贡献值。

| 用户类型 | `加班2局`消费 | `加班4局`消费 | `加班6局`消费 |
| --- | ---: | ---: | ---: |
| 会员 | 299贡献 | 598贡献 | 897贡献 |
| 非会员、普通钻石贡献用户 | 398贡献 | 796贡献 | 1194贡献 |
| 星守护用户 | 按当前余额消费，398贡献对应2局 | 按当前余额消费 | 按当前余额消费 |

加班规则：

- 每场每人累计最多加班6局，已完成、排队中和待执行的局数都计入上限。
- 加班N局中的N建议只允许2、4、6，且不能超过本场剩余加班局数。
- 贡献值不足或超过6局上限时，整条指令拒绝，不自动截断。
- 加班成功后进入独立加班队列，不改变基础区和置顶区顺序。
- `取消上车`不清除加班队列，应使用`取消加班`单独清理。

4. 消费原子性

每条消费指令必须按以下顺序在一个事务内完成：

1. 解析用户、指令和局数。
2. 校验场次、用户身份和队列上限，计算实际进入超车队列的局数。
3. 根据指令接受前的基础支持状态计算费用，并校验贡献值余额。
4. 锁定用户额度账本，扣除实际消费值。
5. 创建或更新队列批次。
6. 写入操作日志并返回结果。

任一步骤失败，整条指令回滚，贡献值和队列都不得改变。

四、权限定义

| 权限 | 来源 | 消费方式 | 场次范围 |
| --- | --- | --- | --- |
| `SYSTEM_QUEUE_ENABLED` | 后台或开播事件 | 只控制普通上车，不控制超车 | 当前场次 |
| `BASE_ENTRY` | 会员身份或99贡献 | 会员免费；非会员每次99贡献 | 当前场次 |
| `PRIORITY_OVERTAKE` | 普通贡献或星守护换算贡献 | 会员每2局299；非会员正常路径每2局398；余额不足398时超车2局可降级扣299并转移基础车位 | 当前场次 |
| `OVERTIME` | 会员299贡献，非会员398贡献 | 每2局一次消费 | 当前场次 |

权限不再以“先发放次数、再扣除次数”的方式维护。后端以“身份 + 当前贡献值余额 + 当前场次状态”实时判定，并记录当次权限快照。

五、开播、关播和重置

1. 开播

- 创建新的 sessionId。
- 归档上一场未正常结束的场次。
- 清空上一场基础、置顶、加班队列及转移、预约、延迟状态。
- 初始化本场贡献值账本和加班6局额度。
- 开启上车功能。
- 保存开播事件日志。

2. 关播

- 先将场次设置为ENDED并关闭上车功能，拒绝新的上车、超车和加班指令。只有“上车功能关闭但场次仍OPEN”时才允许继续超车。
- 保存基础上车列表、置顶批次、加班批次和贡献值余额。
- 保存本场全部弹幕、消费、队列变化、权限和异常日志。
- 将场次设置为ENDED，再清理运行态。
- 本场贡献值、星守护换算值和加班额度不能带入下一场。

3. 重复事件

- 重复开播不重复创建场次、不重复增加星守护贡献、不重复清空队列。
- 重复关播不重复归档、不重复扣除贡献、不重复清空队列。
- 重复礼物事件不重复增加贡献值，使用 giftEventId 或 orderId 识别。

六、日志与复盘

每场直播必须追加保存：

- 原始弹幕和发送者。
- 开播、关播和后台操作。
- 贡献值增加、扣除和余额变化。
- 上车、超车、加班、转移、换位、延迟和取消操作。
- 操作前状态、操作后状态、处理结果和失败原因。
- 用户身份、贡献来源和权限快照。

建议日志字段：

```text
sessionId
sequenceNo
operationId
giftEventId
userId
commandType
rawMessage
requestedGames
consumedContribution
balanceBefore
balanceAfter
queueEntryId
beforeState
afterState
resultCode
receivedAt
processedAt
operatorId
```

前端支持上滑查看已游玩用户，回顾模式保持10秒后自动跳回当前玩家。下播复盘按 sessionId 加载只读快照和完整日志，不修改原始数据。

七、统一反馈

场景	反馈
贡献值不足上车	暂不满足上车权限，当前还需要99贡献
贡献值不足超车	暂不满足超车权限，当前还需要X贡献
上车功能关闭但场次仍OPEN	上车指令拒绝；超车按贡献值和队列上限正常处理
贡献值不足加班	暂不满足加班权限，当前还需要X贡献
会员已有未完成基础车位	您当前已有基础车位，请完成后再上车
加班达到6局	本场您的加班额度已达到6局上限
加班超过剩余额度	本场您还可加班X局，请重新发送“加班X局”
未开播	当前未开播，上车功能未开启
重复礼物事件	该礼物事件已处理，不重复增加贡献

八、后端实现约束

1. 使用服务端递增 sequenceNo 处理同一时间到达的弹幕。
2. 使用 operationId 保证指令、礼物、开关播和人工操作幂等。
3. 贡献值扣除、队列更新和日志写入必须使用事务。
4. 主队列和加班队列分别维护，不使用单一用户位置字段覆盖多个批次。
5. 开播重置前先归档上一场，禁止直接覆盖未归档数据。
6. 后台手动清空只清理运行态，不删除日志；人工修复必须记录原因和前后状态。
7. 提供按 sessionId 查询贡献账本、基础列表、队列批次、权限变化和操作日志的接口。
