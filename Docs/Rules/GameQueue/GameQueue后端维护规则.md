# GameQueue 后端维护规则

本文定义 GameQueue 的直播场次、自动重置、历史留存、操作日志和权限管理规则。它与用户弹幕指令规则配套使用，重点约束后端状态，不替代前端投屏文案。贡献值消费细则以 [后端规则.txt](后端规则.txt) 为准。

## 1. 运行状态

系统按直播场次维护运行状态：

| 状态 | 含义 | 是否接受上车类弹幕 |
| --- | --- | --- |
| `CLOSED` | 未开播或已关播 | 否 |
| `OPEN` | 当前场次正在直播 | 是 |
| `ENDED` | 当前场次已结束，正在保留复盘数据 | 否 |

每场直播必须生成唯一 `sessionId`。基础区、置顶区、加班区、转移标记、预约、延迟和本场额度都必须关联 `sessionId`，不能跨场次复用。

## 2. 开播与关播自动处理

### 2.1 开播事件

当后端读取到开播弹幕或收到开播事件时，执行以下流程：

1. 校验事件是否为本场第一次有效开播。
2. 归档上一场仍处于运行态的场次；上一场没有关播事件时，也必须记录为异常结束。
3. 创建新的 `sessionId`，记录 `startedAt`、开播事件来源和操作人。
4. 清空上一场的运行态：基础队列、置顶批次、加班队列、转移标记、预约、延迟标记和本场额度。
5. 将上车功能设置为 `enabled`，允许接收 `上车`、超车、加班等指令。
6. 写入一条不可修改的“场次开播”日志。

重复收到开播事件时不得再次清空队列。当前状态已经是 `OPEN` 时，应保持当前场次不变，并记录“重复开播事件”。

### 2.2 关播事件

当后端读取到关播弹幕或收到关播事件时，执行以下流程：

1. 先将场次状态设置为 `ENDED`，再将上车功能设置为 `disabled`，拒绝后续新的上车、超车和加班指令。
2. 冻结当前基础上车列表、置顶批次、加班批次和各类剩余局数。
3. 保存本场最终基础队列快照，供争议处理和下播后复盘。
4. 保存本场完整弹幕指令日志、权限日志、队列变化日志和异常日志。
5. 记录 `endedAt`、关播事件来源、操作人和最终统计数据。
6. 将场次状态设置为 `ENDED`；是否立即清理内存中的运行态由实现决定，但不得影响已保存的历史数据。

重复收到关播事件时不得重复归档或重复扣减额度，只记录重复事件。

### 2.3 事件与指令的边界

| 场景 | 处理 |
| --- | --- |
| `CLOSED` 状态收到 `上车`、超车或加班 | 拒绝，回复“当前未开播，上车功能未开启” |
| `OPEN` 状态收到正常指令 | 按当前 `sessionId` 处理 |
| `OPEN` 状态但上车功能关闭时收到 `上车` | 拒绝，不扣贡献 |
| `OPEN` 状态但上车功能关闭时收到超车 | 忽略上车开关，按贡献值和主队列上限处理 |
| `ENDED` 状态收到正常指令 | 拒绝，不写入新的队列状态；原始弹幕仍写入日志 |
| 开播后收到上一场延迟弹幕 | 按收到时间判断，只能进入新场次，不能恢复上一场状态 |
| 关播和普通弹幕同时到达 | 按服务端 `sequenceNo` 排序，关播序号之后的普通指令拒绝 |

## 3. 基础上车列表与历史留存

### 3.1 当前列表

运行期间必须保留可直接读取的基础上车列表，至少包含：

- 当前基础区位置和位置序号。
- 用户标识、显示名称和原始上车时间。
- 基础局数、剩余局数、延迟标记和预约标记。
- 是否存在置顶批次。
- 车位上的转移标记及接收方。
- 最近一次变更的 `sequenceNo` 和 `updatedAt`。

当前列表用于投屏、查询车位、人工处理争议和实时纠错，不应只通过重新扫描弹幕临时计算。

### 3.2 每场直播的历史数据

每场直播至少保留以下数据：

| 数据 | 留存内容 | 用途 |
| --- | --- | --- |
| 场次记录 | `sessionId`、开播、关播、状态、操作人 | 判断场次边界 |
| 基础队列快照 | 开播初始、每次变化后的列表、关播最终列表 | 复盘基础上车顺序 |
| 弹幕指令日志 | 原始弹幕、发送者、接收时间、解析结果、处理结果 | 还原用户操作 |
| 队列操作日志 | 上车、超车、转移、换位、延迟、取消、加班等变化 | 定位状态变化 |
| 权限日志 | 授权、撤销、来源、有效期、权限快照 | 处理权限争议 |
| 异常日志 | 解析失败、重复事件、超限、并发冲突、人工修复 | 排查后端问题 |

日志采用追加写入，不因开播重置或关播清理而删除。建议基础队列至少保存“当前快照”和“关播最终快照”；如需要完整复盘，则每次成功或失败的指令都保存变更前后摘要。

### 3.3 日志字段建议

```text
sessionId
sequenceNo
operationId
eventType
rawMessage
commandType
userId
targetUserId
requestedGames
effectiveGames
queueType
queueEntryId
beforeState
afterState
resultCode
resultMessage
permissionSnapshot
receivedAt
processedAt
operatorId
```

`rawMessage` 用于还原原始弹幕，`beforeState` 和 `afterState` 用于定位争议。日志中的用户隐私字段应按平台数据保留策略脱敏或限制访问。

## 4. 上车、超车和加班权限

权限不再预先拆成99贡献次数和299贡献次数，而是根据用户身份、当前场次和 `contributionBalance` 实时判断。完整扣除公式、星守护换算和会员规则见 [后端规则.txt](后端规则.txt)。

### 4.1 上车

`上车`不需要单独的用户权限，但必须满足：

- 当前场次状态为 `OPEN`。
- 上车功能开关为 `enabled`。
- 会员余额规则允许免费上车，或非会员余额至少为99贡献。
- 弹幕格式解析成功。

上车成功后，会员不扣贡献；非会员扣除99贡献，并创建基础车位。关播后不能继续向当前场次追加新的车位。

### 4.2 超车

以下指令按局数和当前基础支持状态消费统一贡献值：

| 用户状态 | `超车2局` | `超车4局` | `超车6局` |
| --- | ---: | ---: | ---: |
| 会员 | 299贡献 | 598贡献 | 897贡献 |
| 非会员当前已有基础车位，余额>=398 | 398贡献 | 796贡献 | 1194贡献 |
| 非会员当前已有基础车位，余额为299~397 | 扣299并转移基础车位 | 不适用 | 不适用 |
| 非会员且当前没有基础车位 | 398贡献 | 796贡献 | 按4局处理，最高796贡献 |

超车处理要求：

- 上表是请求局数全部生效时的费用；实际费用按本次实际进入超车队列的局数计算，包含新增局数和从基础车位转入的局数。
- `超车费用 = effectivePriorityGames ÷ 2 × 每2局单价`，没有进入超车队列的局数时不扣贡献。
- 无基础车位时置顶区硬上限为4局，不能通过超车达到6局。
- 无基础车位发送`超车6局`按4局处理：从0局增加4局扣796，从2局增加2局扣398，已有4局则拒绝且不扣贡献。
- 每2局单价使用指令接受前的基础支持状态，不能在执行中途改变。
- 非会员已有基础车位且余额>=398时，扣398并新增超车批次，基础车位保留。
- 非会员已有基础车位且余额为299~397时，只有`超车2局`可以降级处理：扣299，将当前最前基础车位转入超车队列并移除原基础位置。
- 非会员没有基础车位时，第一次直接超车必须余额达到398，扣398后加入超车队列，但不创建基础车位。
- 非会员已有基础车位时余额500发送`超车2局`，应扣398、新增2局超车批次、保留基础车位，余额剩102。
- 当前场次必须为 `OPEN`，但超车不检查上车功能开关。
- 非会员没有基础车位时，每2局额外扣99基础支持贡献；该费用只支持本次超车，不创建基础车位。
- 后端校验当前用户状态、贡献值余额和主队列局数上限。
- 不再单独发放或维护“基础权限次数”和“超车权限次数”。
- 每次成功指令生成独立置顶批次，后续超车不能回到旧批次位置。
- 贡献值不足时整条指令拒绝，不扣除部分贡献。

### 4.3 加班

加班权限与主队列状态独立。用户不在基础队列时，只要贡献值余额足够，也可以发送加班指令。

| 用户类型 | `加班2局`消费 | 本场上限 |
| --- | ---: | ---: |
| 会员 | 299贡献 | 6局 |
| 非会员、普通钻石贡献用户 | 398贡献 | 6局 |
| 星守护用户 | 按当前贡献值余额消费 | 6局 |

加班处理要求：

- 用户必须处于 `OPEN` 场次。
- 已完成、排队中和待执行的局数都计入每人6局上限。
- 贡献值不足或请求超过剩余额度时整条指令拒绝，不自动截断。
- 加班成功后进入独立加班队列，不改变基础区和置顶区。
- `取消上车`不清除加班队列，使用`取消加班`单独处理。

无权限或余额不足时：

```text
暂不满足加班权限，请检查当前贡献值余额。
```

## 5. 权限、额度和重置的关系

开播或关播自动重置的是本场运行态和本场额度，不应默认删除用户的长期权限记录：

| 对象 | 开播时 | 关播时 |
| --- | --- | --- |
| 上车功能开关 | 设置为开启 | 设置为关闭 |
| 基础队列 | 新建空队列 | 冻结并保存最终快照 |
| 置顶队列 | 新建空批次列表 | 保存最终批次状态 |
| 加班队列 | 新建空队列，额度归零 | 保存最终批次和额度 |
| 加班 6 局额度 | 重置为 0/6 可用 | 固化本场统计 |
| 本场贡献值账本 | 新建普通贡献和星守护换算余额 | 保存最终余额和消费记录 |
| 长期身份 | 保留会员和星守护状态记录 | 保留身份日志 |
| 本场权限快照 | 新场次重新记录 | 随日志归档 |
| 历史日志 | 保留 | 保留 |

## 6. 后端维护建议

1. 所有场次和队列写入操作使用事务，避免“日志成功但状态失败”或“状态成功但日志丢失”。
2. 使用服务端递增 `sequenceNo` 处理同一时间到达的弹幕，不能依赖客户端时间排序。
3. 使用 `operationId` 保证开播、关播、转移和权限操作幂等，重复弹幕不能重复扣额度或重复加队列。
4. 开播重置前先检查上一场是否已经归档；未归档时先归档再清理，禁止直接覆盖。
5. 提供按 `sessionId` 查询基础列表、完整弹幕日志、队列变化和权限变化的后台接口。
6. 提供“只读复盘模式”，复盘历史场次时禁止修改原始队列和日志。
7. 人工修复必须使用独立操作类型并记录操作人、原因、修复前后状态，禁止直接修改原始日志。
8. 对日志访问按角色授权：主播可查看本场，管理员可查看历史和执行修复，普通用户只能查询自己的状态。
